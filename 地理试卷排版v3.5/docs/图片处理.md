# 图片处理流程分析

## 一、总览：Word → Markdown 的完整流水线

```
原始试卷.docx
    │
    ▼  Step1.1: clean_docx.py
cleaned.docx（浮动图→内嵌图，WMF标点替换，品牌水印清除）
    │
    ▼  Step1.2: extract_images.py
cleaned_no_images.docx + images/ + image_manifest.json
    │
    ▼  Step1.3: utils.py::docx_to_markdown()
content.md + tables.json
    │
    ▼  Step2 (AI): tag_structure
structure.json
    │
    ▼  Step3 (AI): tag_placeholders
with_placeholders.json（含 anchor 占位符）
    │
    ▼  Step4 (AI): tag_images
anchor_descriptions.json
    │
    ▼  Step5: map_images.py
final_exam.json（占位符→图片映射完成）
    │
    ▼  Step6: typeset_exam.py
排版后的 final_exam.docx
```

**核心原则**：程序不直接将 Word "转换"为 Markdown——而是先清洗、提取图片、再转为 Markdown 文本。图片以占位符（`{{image:xxx}}` / `{{symbol:xxx}}`）形式嵌入 Markdown，最终通过映射关系回插。

## 二、图片处理三阶段

### 阶段 A：清洗期（clean_docx.py）——在原始 docx 中处理图片

此阶段直接操作 Word XML，对图片做预处理，为后续提取做准备。

#### 1. 记录原始图片类型 — `record_original_image_types()`

**时机**：在浮动图→内嵌图转换之前执行。

**作用**：扫描文档中所有 `<w:drawing>` 元素，判断每张图片的原始定位类型，写入 `_original_image_types.json`。

| 原始类型 | XML 特征 | 含义 |
|---------|---------|------|
| `inline` | `<wp:inline>` 子元素 | 内嵌图片，随文字流动，位置确定 |
| `anchor` | `<wp:anchor>` 子元素 | 浮动图片，可浮于文字上方/下方，位置不确定 |
| `vml` | `<v:imagedata>` 元素 | VML 旧式图片 |
| `unknown` | 以上均不匹配 | 未知类型 |

**输出**：
```json
{
  "rId7": "inline",
  "rId8": "anchor",
  "rId9": "inline"
}
```

此文件是 v3.5 双轨分流的基础——inline 图由代码确定处理，anchor 图由 AI 介入。

#### 2. WMF/EMF 矢量图片文字替换 — `replace_image_punctuation()`

**问题**：学科网等平台下载的试卷中，标点符号（如 `.`）、汉字（如 `的`）常以 WMF/EMF 矢量图片形式嵌入（由 MathType 生成）。这些"图片"本质是文字，需要还原为文本。

**处理流程**：

```
遍历段落中每个 run
  → 检测是否含 <w:drawing>
    → 获取 rId → 查找媒体文件信息（大小、扩展名）
      → 判断是否为"疑似文字图片"：
          file_size < 2KB 或 file_ext ∈ {.wmf, .emf}
        → 策略1: WMF/EMF 直接提取文本
            从 WMF 二进制数据中解析 EXTTEXTOUT 记录（0x0A32）
            或搜索末尾嵌入的 MathML XML（<mo>/<mi>/<mn> 标签）
          → 策略2: 上下文推断
            根据前后文本推断标点类型（如选项编号后的点号）
          → 提取成功：在图片位置插入文字 run，删除图片 run
          → 提取失败：加入 pending_images.json
```

**上下文推断规则**（`_infer_punctuation()`）：

| 场景 | 前文模式 | 后文模式 | 推断结果 |
|------|---------|---------|---------|
| 选项编号点号 | `[ABCD]$` | 选项文字 | `.` |
| 题号点号 | `\d+$` | 非数字 | `.` |
| 子问题编号点号 | `[）)]\d*[）)]?$` | — | `.` |
| 句子结尾句号 | CJK字符 | 空/新段落 | `。` |
| 数字间小数点 | `\d$` | `^\d` | `.` |

**输出**：
- 替换成功的图片：直接在 docx XML 中完成文字替换
- 替换失败的图片：输出 `pending_images.json`，供后续人工/AI 识别

#### 3. 浮动图片转内嵌 — `rule_1_19_convert_floating_images()`

**作用**：将所有 `<wp:anchor>` 转换为 `<wp:inline>`，确保排版阶段图片位置可控。

**转换方式**：
1. 创建新的 `<wp:inline>` 元素
2. 将 anchor 的子元素移入 inline（跳过定位相关元素：`simplePos`, `positionH`, `positionV`, `wrapNone` 等）
3. 删除原 anchor 元素

**注意**：此操作不可逆，因此在转换前先通过 `record_original_image_types()` 保存了原始类型信息。

#### 4. 其他图片相关清洗

| 规则 | 函数 | 说明 |
|------|------|------|
| 1.17 | `rule_1_17_remove_exam_name_images()` | 删除考试名称前5段中的图片（通常为平台 logo） |
| 1.7 | `rule_1_7_vector_images()` | 仅记录剩余矢量图片信息（标点类已在步骤2替换） |
| — | `clean_image_descriptions()` | 清理图片描述属性（descr/name）中的品牌关键词 |

### 阶段 B：提取期（extract_images.py）——分离图片与文档

此阶段将图片从 docx 中完全分离，生成独立的图片文件和元数据清单。

#### 1. 提取所有图片 — `extract_all_images()`

**遍历范围**：文档 body 中所有段落（递归查找，包括表格内的段落）。

**处理流程**：

```
遍历每个段落的每个 run
  → 检测 <w:drawing> 元素
    → 获取图片类型 (inline/anchor/vml)
    → 获取 rId → 查找媒体路径
    → 获取文件信息（大小、扩展名）
    → 获取上下文文字（before_text / after_text）
    → 从 docx ZIP 包读取图片二进制数据
    → 保存为 images/img_001.png, img_002.wmf 等
    → 记录到 image_manifest.json
```

**image_manifest.json 结构**：

```json
{
  "source_docx": "cleaned.docx",
  "extract_time": "2026-07-13T10:00:00",
  "total_images": 3,
  "images": [
    {
      "image_id": "img_001",
      "image_file": "img_001.png",
      "image_path": "/abs/path/to/images/img_001.png",
      "original_media_path": "word/media/image1.png",
      "relationship_id": "rId7",
      "file_size": 45678,
      "file_ext": ".png",
      "image_type": "inline",
      "original_type": "inline",      // ← v3.5 新增，来自 _original_image_types.json
      "paragraph_index": 12,
      "run_index": 3,
      "paragraph_text": "图1为某区域等高线示意图",
      "context_before": "图1为某区域",
      "context_after": "示意图"
    }
  ]
}
```

#### 2. 合并原始图片类型 — `_merge_original_types()`

v3.5 新增：读取 `_original_image_types.json`，按 `relationship_id` 将 `original_type` 字段合并到 manifest 的每条记录中。

这使得后续 `map_images.py` 能够按 original_type 实施双轨分流。

#### 3. 删除文档中所有图片 — `remove_all_images()`

**操作**：
1. 删除所有 `<w:drawing>` 元素
2. 检查删除后 run 是否为空（无文字、无图片），若空则删除整个 run

**结果**：输出 `cleaned_no_images.docx`（纯文本，无图片）。

### 阶段 C：Markdown 转换期（utils.py::docx_to_markdown）——图片变为占位符

此阶段将纯文本 docx 转为 Markdown，同时将图片位置标记为占位符。

#### 核心转换逻辑

```python
def docx_to_markdown(docx_path, md_path, image_manifest_path=None, tables_path=None):
```

**遍历方式**：按 XML 顺序遍历 `<w:p>`（段落）和 `<w:tbl>`（表格），保持原始顺序。

**图片占位符插入策略**：

```
对于每个段落：
  → 检查 image_manifest 中是否有属于该段落的图片
    → 如果有 inline 图片：
        file_size < 2KB → 插入 {{symbol:img_xxx}}
        file_size >= 2KB → 插入 {{image:img_xxx}}
    → 如果有 anchor 图片：
        不在此处标记（由 Step3 AI 处理）
```

**占位符类型**：

| 占位符 | 含义 | 来源 |
|--------|------|------|
| `{{image:img_001}}` | 内容图片（≥2KB 的 inline 图） | extract_images 的 manifest |
| `{{symbol:img_003}}` | 符号图片（<2KB 的 inline 图） | extract_images 的 manifest |
| `{{table:table_001}}` | 表格占位符 | docx 中的 `<w:tbl>` |
| `{{image:ph_anchor_001}}` | 浮动图占位符 | Step3 AI 生成 |

**文本处理**：
- 上标：`<w:vertAlign val="superscript">` → `<sup>文本</sup>`
- 下标：`<w:vertAlign val="subscript">` → `<sub>文本</sub>`
- 表格：输出为 `{{table:NNN}}` 占位符 + 结构化 `tables.json`（方案C）

**输出**：
- `content.md`：纯 Markdown 文本，图片以占位符代替
- `tables.json`：结构化表格数据（含合并信息）

## 三、图片映射（map_images.py）——v3.5 双轨分流

### 为什么需要双轨？

| 图片类型 | 位置确定性 | 处理方式 |
|---------|----------|---------|
| inline（内嵌） | 高——随文字流动，paragraph_index 即位置 | 代码确定（Track 1） |
| anchor（浮动） | 低——可能浮于任意位置，paragraph_index 仅是锚点 | AI 语义匹配（Track 2） |

### Track 1：代码确定路径（inline 图片）

```
inline 图片的 placeholder_id = image_id
  → 与 content.md 中 {{image:img_xxx}} 一一对应
  → 置信度固定 0.95
  → track: "code"
```

**逻辑**：内嵌图片的占位符 ID 就是图片 ID，无需语义匹配，位置由段落顺序确定。

### Track 2：AI 匹配路径（anchor 图片）

```
1. 按 original_type 分类图片：
     inline → Track 1
     anchor/vml/unknown → Track 2
     < 2KB → 标记为符号小图，跳过映射

2. 占位符分类：
     有效占位符：有具体上下文（如"位置如下图"）
     泛型占位符：仅"题干明确提到图片关键词"（如"阅读图文材料"）

3. 匹配策略：
     按 paragraph_index 排序 anchor 图
     有效占位符按题目顺序排列
     一一映射（anchor 图按顺序分配给有效占位符）

4. 置信度计算：
     基础: 0.70 (anchor) / 0.65 (unknown)
     +0.2: 关键词匹配 ≥ 2 个
     +0.1: 关键词匹配 = 1 个
     上限: 0.95 (anchor) / 0.90 (unknown)

5. 冗余检测：
     同一题中泛型占位符与已映射的具体占位符 → 合并映射
```

### 映射结果

```json
{
  "image_mapping": [
    {
      "placeholder_id": "img_001",
      "image_id": "img_001",
      "confidence": 0.95,
      "reason": "内嵌图片，位置确定（段落12）",
      "track": "code"
    },
    {
      "placeholder_id": "ph_anchor_001",
      "image_id": "img_005",
      "confidence": 0.90,
      "reason": "浮动图+关键词匹配(2个): 等高线, 示意图",
      "track": "ai"
    }
  ]
}
```

## 四、排版回插（typeset_exam.py）——图片回归 Word

### ImageResolver 解析链路

```
placeholder_id → image_mapping → image_id → images[].file_name → 文件系统路径
```

```python
class ImageResolver:
    # 构建 image_id → file_name 映射
    id_to_file = {img['image_id']: img['file_name'] for img in images_data}
    # 构建 placeholder_id → 文件路径 映射
    for mapping in image_mapping_data:
        ph_id → img_id → file_name → full_path
```

### 图片在排版中的插入位置

| 位置 | 处理逻辑 |
|------|---------|
| 题干 | 按 `{{image:ph_xxx}}` 占位符分段，纯文本段落 + 居中图片段落交替 |
| 选项 | 选项含图片占位符时使用规则5（2x2 图片选项排版） |
| 材料 | 选择题：文本+引导语先渲染，图片延迟到后面；非选择题：按段顺序 |

## 七、图片大小阈值与分类

| 条件 | 分类 | 处理方式 |
|------|------|---------|
| file_size < 2KB 且 WMF/EMF | 疑似文字图片 | 尝试 WMF 提取/上下文推断 |
| file_size < 2KB 且非 WMF/EMF | 疑似符号图片 | 上下文推断，失败则 pending |
| file_size < 2KB 且 original_type=inline | 符号小图 | Markdown 中标记为 `{{symbol:}}` |
| file_size ≥ 2KB 且 original_type=inline | 内容图片 | Markdown 中标记为 `{{image:}}`，Track 1 映射 |
| original_type=anchor | 浮动图片 | 不在 MD 中标记，Track 2 AI 映射 |
| file_size < 2KB 且 original_type=anchor | 符号级浮动图 | 跳过映射，写入 warnings |
